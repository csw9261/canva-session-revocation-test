## 1. Stateless 세션과 취소 문제

### 1.1 두 가지 세션 모델

| | Stateful (서버 세션) | Stateless (암호화 쿠키 / JWT) |
|---|---|---|
| 세션 정보 위치 | 서버 저장소 | 쿠키 안 |
| 요청당 조회 | 1회 이상 | 0회 |
| 확장 | 저장소가 병목 | 게이트웨이만 늘리면 됨 |
| 로그아웃 | 저장소에서 지우면 끝 | **어려움** — 이미 발급한 쿠키를 회수할 수 없음 |

Canva는 stateless를 택함. 요청당 조회 0회를 얻는 대신 **취소 능력을 잃음**.
세션 취소 인프라 전체가 이 잃어버린 능력을 되사오는 비용임.

### 1.2 왜 취소가 어려운가

stateless의 핵심은 "서버가 아무것도 기억하지 않는다"임.
그런데 취소는 본질적으로 "이건 이제 무효다"를 **기억하는 일**임. 정의상 충돌함.

그래서 나오는 해법이 세 가지.

| 해법 | 방식 | 문제 |
|---|---|---|
| 짧은 만료 | 토큰 수명을 몇 분으로 | 재로그인·갱신이 잦아짐. 그 몇 분 동안은 여전히 유효 |
| 매 요청 조회 | 요청마다 유효성 확인 | stateless를 포기하는 것 |
| **취소 목록** | 무효화된 것만 기억 | 목록 관리·전파 문제 ← 이 프로젝트 |

취소 목록이 성립하는 이유는 **예외만 기억하면 되기 때문**임.
기본은 통과, 목록에 있으면 차단. 로그아웃은 전체 세션 대비 드문 사건이라 목록이 작게 유지됨.
전체 세션이 수억 개여도 12시간 내 취소는 100만 건 수준인 게 이 때문.

### 1.3 왜 세션 ID가 아니라 principal + 시각인가

취소 1건을 "세션 ID 하나 무효"로 표현하면, 사용자가 기기 5대에서 로그인했을 때 로그아웃 1회에 5건이 생김.
대신 **"이 사용자의, 이 시각 이전에 시작된 세션 전부 무효"** 로 표현하면 몇 개든 1건임.

```
취소 = (principal, login_timestamp)
검사 = 쿠키의 principal로 조회 → 찾은 취소의 timestamp보다 쿠키의 login_timestamp가 이르면 차단
```

목록 크기를 세션 수가 아니라 **취소 이벤트 수**에 비례하게 만드는 설계임.
권한 변경처럼 "로그아웃은 아니지만 쿠키 내용이 낡음"인 경우도 같은 구조로 표현 가능 — 그래서 플래그 비트가 필요해짐.

### 1.4 쿠키 암호화

서명(HMAC)만 하면 내용이 그대로 보임. 쿠키 안에 권한과 역할이 들어 있으므로 노출되면 안 됨.
그래서 **AEAD** (Authenticated Encryption with Associated Data) 를 씀 — 기밀성과 무결성을 한 번에.

- 대표적으로 AES-GCM, ChaCha20-Poly1305
- 검증 실패 = 위조 → 그 자리에서 401
- nonce 재사용 금지가 AES-GCM의 함정. 건마다 랜덤 nonce를 쓰고 쿠키에 같이 실음

**어디에 쓰이나**: auth 서비스의 쿠키 발급, gateway의 복호화·검증

## 2. HTTP 조건부 요청

이 시스템의 동시성 제어와 폴링 효율이 전부 여기 얹혀 있음.

### 2.1 ETag

서버가 리소스를 줄 때 현재 내용의 버전 식별자를 같이 줌. 내용이 바뀌면 ETag도 바뀜.

```
GET /chunks/1755100800.bin
→ 200 OK
  ETag: "abc123"
  <바이너리 데이터>
```

**ETag는 불투명(opaque) 토큰으로 다뤄야 함.** 내용 해시라고 가정하고 직접 계산하려 들면 안 됨.
S3의 경우 단일 PUT으로 올린 평문 객체는 ETag가 본문 MD5지만, 멀티파트 업로드나 암호화가 걸리면 규칙이 달라짐.
받은 값을 그대로 되돌려주는 용도로만 씀.

### 2.2 조건부 GET — 폴링 비용 절감

```
GET /chunks/1755100800.bin
If-None-Match: "abc123"

→ 304 Not Modified   안 바뀜. 본문 없음 (대역폭 0)
→ 200 OK + 본문      바뀜. 새 ETag 동봉
```

브라우저 캐시가 쓰는 그 메커니즘임.
게이트웨이가 청크를 폴링할 때 이걸 쓰면, 안 바뀐 청크에 대해 16MB를 다시 받지 않고 304만 받음.

### 2.3 조건부 PUT — 동시성 제어

같은 원리를 쓰기에 적용함.

```
PUT /chunks/1755100800.bin
If-Match: "abc123"
<수정한 데이터>

→ 200 OK                    현재 ETag가 abc123 → 내 쓰기 반영됨
→ 412 Precondition Failed   그 사이 누가 바꿈 → 내 쓰기 거부됨
```

핵심은 **412를 받으면 내 쓰기가 아예 일어나지 않았다는 것**임.
덮어쓰기가 부분적으로 실패한 게 아니라, 시도 자체가 거부됨.

### 2.4 정리

| 헤더 | 붙는 곳 | 의미 | 조건 충족 | 조건 불충족 |
|---|---|---|---|---|
| `If-None-Match: "etag"` | GET | 다를 때만 달라 | 200 + 본문 | **304** |
| `If-Match: "etag"` | PUT | 그대로일 때만 써라 | 200 | **412** |
| `If-None-Match: *` | PUT | 없을 때만 만들어라 | 200 | **412** |

`If-None-Match: *` 는 새 청크를 처음 만들 때 씀.
워커 둘이 동시에 같은 구간의 첫 청크를 만들려 하면 한쪽만 성공하고, 다른 쪽은 412를 받고 "이미 있구나" 하며 읽기로 전환함.

### 2.5 strong ETag와 weak ETag

`W/"abc123"` 처럼 `W/` 가 붙으면 weak ETag임 — "의미상 같음"만 보장하고 바이트 단위 동일성은 보장하지 않음.

**`If-Match`는 strong 비교를 요구하므로 weak ETag를 쓸 수 없음.**
조건부 PUT을 쓰려면 서버가 strong ETag를 줘야 함. 스파이크에서 확인할 항목 중 하나.

**어디에 쓰이나**: worker의 청크 갱신(2.3), gateway의 청크 폴링(2.2), 새 청크 생성(2.4)

## 3. Lost update와 낙관적 동시성 제어

### 3.1 문제

객체 스토리지는 부분 수정이 없음. 객체를 바꾸려면 통째로 다시 써야 함.
그래서 청크 갱신이 **read-modify-write**가 됨.

```
GET 청크 → 메모리에서 정렬 배열에 삽입 → PUT 청크
```

워커가 둘 이상이면 이렇게 겹칠 수 있음.

```
워커 A: GET(v1) ──────── 삽입(a) ──────── PUT(v1+a)
워커 B:      GET(v1) ──────── 삽입(b) ──────── PUT(v1+b)   ← A의 결과를 통째로 덮어씀

최종 객체: v1+b     a는 사라짐
```

이게 **lost update**임.

### 3.2 왜 특히 위험한가

- **조용함** — 두 PUT 모두 200을 받음. 에러가 안 남고 로그에도 안 남음
- **이 시스템에서는 보안 사고** — 사라진 a가 "이 사용자 로그아웃"이면, 로그아웃했는데 세션이 계속 살아있음
- **재현이 어려움** — 타이밍에 의존하므로 테스트에서 잘 안 잡힘

### 3.3 조건부 PUT이 막는 방식

```
워커 A: GET  → ETag "v1"
워커 B: GET  → ETag "v1"
워커 A: PUT If-Match "v1" → 200 OK.   객체는 이제 "v2" (a 포함)
워커 B: PUT If-Match "v1" → 412!      현재는 "v2"라 거부
워커 B: 다시 GET → "v2" (a가 들어있음) → b 삽입 → PUT If-Match "v2" → 200 OK

최종: a도 b도 살아있음
```

B가 강제로 **A의 결과 위에서 다시 작업**하게 됨.

```go
// 워커의 청크 갱신 루프
for {
    data, etag := s3.Get(key)                  // 현재 청크와 버전
    merged := insertSorted(data, batch)        // 메모리에서 병합
    err := s3.Put(key, merged, ifMatch(etag))
    if err == nil { break }                    // 성공
    if isPreconditionFailed(err) { continue }  // 누가 먼저 씀 → 다시 읽고 재시도
    return err
}
```

이 몇 줄이 "워커를 여러 개 돌려도 취소가 유실되지 않는다"의 전부임.

### 3.4 이건 CAS임

멀티스레드 프로그래밍의 compare-and-swap과 같은 구조임.

```go
atomic.CompareAndSwapUint64(&v, old, new)   // v가 아직 old일 때만 new로
```

```
PUT If-Match: "abc123"                      // ETag가 아직 abc123일 때만 새 내용으로
```

ETag가 `old` 자리를 대신함. DB의 낙관적 잠금과도 같은 패턴임.

```sql
UPDATE chunks SET data = ?, version = 6 WHERE id = ? AND version = 5
-- 영향받은 행이 0이면 412와 같은 상황. 다시 읽고 재시도
```

### 3.5 낙관적 vs 비관적

| | 비관적 (pessimistic) | 낙관적 (optimistic) |
|---|---|---|
| 방식 | 먼저 잠금 획득 후 작업 | 그냥 작업하고 쓸 때 검사 |
| 필요한 것 | 잠금 서버, 임대 만료, 장애 처리 | 조건부 쓰기 하나 |
| 충돌 시 | 대기 | 재시도 |
| 유리한 상황 | 충돌 잦음 | **충돌 드묾** |

취소 워커는 청크 하나에 붙는 워커가 몇 개 안 되므로 충돌이 드묾. 낙관적이 맞음.

### 3.6 재시도할 때 주의할 것

- **백오프와 지터** — 즉시 재시도하면 같은 상대와 계속 부딪힘. 지수 백오프 + 랜덤 지터를 넣어야 함
- **라이브락** — 충돌이 잦으면 아무도 진척을 못 냄. 원문이 리더 선출을 최적화로 둔 이유가 이것
- **재시도 상한** — 무한 루프 방지. 상한 초과는 알람 대상
- **매 시도마다 다시 읽어야 함** — 이전에 읽은 데이터를 재사용하면 조건부 PUT의 의미가 없어짐

### 3.7 ABA 문제는?

CAS에는 보통 ABA 문제가 따라옴 — 값이 A → B → A로 돌아오면 안 바뀐 것처럼 보임.

이 시스템에서는 걱정할 필요 없음.

- 청크 갱신이 **append-only**임. 취소가 추가되기만 하고 제거되지 않으므로 내용이 이전 상태로 되돌아갈 수 없음
- 따라서 ETag도 이전 값으로 되돌아가지 않음

단, 이건 **append-only라는 불변식이 유지될 때만** 참임. 나중에 청크에서 뭔가 지우는 기능을 넣으면 이 논리가 깨짐.

**어디에 쓰이나**: worker 다중 실행, E2E 성공 기준 4번(유실 0건 확인)

## 4. 리더 선출이 정확성을 보장하지 못하는 이유

원문에서 가장 배울 만한 지점이라 따로 정리함.

### 4.1 순진한 기대

"리더를 뽑아서 리더만 쓰게 하면 동시 쓰기가 없으니 안전하지 않나?"

### 4.2 반례

```
1. 노드 A가 리더가 됨
2. A: 청크를 읽고, 병합하고, PUT을 던지기 직전
3. A가 멈춤 — GC pause, 스케줄러 선점, 네트워크 지연, 어느 것이든
4. A의 리더 임대가 만료됨. 노드 B가 새 리더가 됨
5. B: 읽고, 병합하고, 씀. 정상 동작
6. A가 깨어남. A는 자기가 아직 리더인 줄 앎. 2번에서 준비한 PUT을 던짐
7. B의 쓰기가 사라짐
```

핵심은 **"내가 리더다"라는 판단과 실제 쓰기 사이에 시간 간격이 있다는 것**임.
그 사이에 리더 자격이 바뀔 수 있고, 멈춰 있던 노드는 그 사실을 알 수 없음.

임대(lease) 만료로 막으려 해도 시계 가정에 기대야 하고, 4번과 6번 사이가 임대 기간보다 길다는 보장이 없음.

### 4.3 조건부 PUT은 이 문제에 면역

A가 6번에서 던지는 PUT은 **2번 시점의 ETag**를 달고 감.
그런데 5번에서 B가 썼으므로 현재 ETag는 다름. → **412**.

리더냐 아니냐를 묻지 않고, **"내가 본 상태가 아직 그대로냐"** 만 물어보기 때문에 시계도 임대도 필요 없음.

### 4.4 그래서 리더 선출의 역할은

정확성이 아니라 **충돌 빈도 감소**임. 3.6의 라이브락을 막는 최적화.

```
정확성  ← 조건부 PUT
효율    ← 리더 선출 (선택)
```

**어디에 쓰이나**: 내 구현에서 ZooKeeper 리더 선출을 빼는 근거. 조건부 PUT만으로 정확성이 확보되므로 없어도 됨

## 5. 비트 패킹과 메모리 레이아웃

### 5.1 16바이트에 뭘 담을 수 있나

담아야 할 것: principal, login timestamp, 플래그.

```
principal      uint64          8바이트    사용자 ID
login_ts_ms    48비트          6바이트    밀리초 단위. 2^48ms ≈ 서기 10889년까지
flags          16비트          2바이트    취소 타입
                              ─────────
                              16바이트
```

밀리초를 48비트에 넣는 게 요점임. 8바이트를 다 쓰면 플래그 자리가 없음.
(원문은 구체적 배치를 밝히지 않고 "some bit twiddling"이라고만 함. 위는 내 후보안이고 [03-design.md](03-design.md)에서 확정함)

### 5.2 Go에서 객체 표현이 왜 큰가

같은 100만 건을 두 방식으로 담으면:

```go
// 밀집: 16MB. 끝.
chunk := make([]byte, 16*1_000_000)

// 객체: 훨씬 큼
type Rev struct {
    Principal uint64      // 8
    LoginTS   time.Time   // 24 (wall uint64 + ext int64 + loc 포인터)
    Flags     uint16      // 2 → 정렬 패딩으로 8
}
revs := make(map[uint64]*Rev, 1_000_000)
```

객체 방식에서 추가로 드는 것:

- **포인터** — 건당 8바이트
- **힙 할당 단위** — Go는 크기 클래스 단위로 할당하므로 실제 크기보다 올림됨
- **map 오버헤드** — 버킷 구조, tophash, 그리고 로드 팩터 때문에 남는 슬롯
- **GC 스캔 비용** — 포인터가 있는 객체 100만 개는 GC가 매번 훑어야 함. `[]byte`는 포인터가 없어서 스캔 대상이 아님

마지막 항목이 중요함. 밀집 바이트 배열은 **GC에게 보이지 않는 데이터**라서 힙이 커져도 GC 부담이 안 늘어남.
원문이 Java에서 87.5%를 줄인 것도 같은 맥락 — 객체 헤더와 참조가 사라짐.

### 5.3 왜 flat 배열이 빠른가

- **캐시 라인** — 64바이트 라인 하나에 16바이트 레코드 4개가 통째로 들어옴
- **포인터 추적 없음** — 역참조마다 캐시 미스 나는 구조가 아님
- **prefetch 친화적** — 주소가 연속이라 하드웨어 프리페처가 잘 맞춤
- **변환 비용 0** — S3에서 받은 바이트를 그대로 씀. 역직렬화 단계 자체가 없음

마지막이 시딩 속도의 핵심임. 게이트웨이가 부팅할 때 하는 일이 다운로드뿐이 됨.

**어디에 쓰이나**: 레코드 포맷 정의, gateway 메모리 사용량

## 6. 이진 탐색의 전제

### 6.1 불변식

**청크는 항상 principal 기준 정렬 상태를 유지해야 함.** 이게 깨지면 조회가 조용히 틀린 답을 냄.

워커가 배치를 삽입할 때마다 정렬을 유지해야 하고, 이게 O(N²)의 출처임.

### 6.2 같은 principal에 취소가 여러 건일 수 있음

한 사용자가 여러 번 로그아웃하면 취소도 여러 건임. 단순 이진 탐색은 그중 아무거나 찾음.
**하한(lower bound)** 을 찾아서 같은 principal 구간 전체를 순회해야 함.

```go
// principal 이상인 첫 인덱스
i := sort.Search(n, func(i int) bool {
    return principalAt(chunk, i) >= target
})
// i부터 principal이 달라질 때까지 순회하며 가장 강한 취소를 찾음
```

### 6.3 청크가 여러 개임

윈도우 안에 청크가 여러 개 있고, 취소는 아무 청크에나 있을 수 있음.
→ **모든 청크에 대해 각각 탐색해야 함.**

```
조회 비용 = O(청크 수 × log(청크당 레코드 수))
```

원문 기준 12시간 / 30분 = 청크 24개. 내 구현도 12분 / 30초 = 24개로 같은 비율.
청크 구간을 줄이면 갱신은 싸지지만 조회는 비싸짐. 이 트레이드오프를 설계에서 의식해야 함.

**어디에 쓰이나**: gateway 검사 로직, 청크 구간 파라미터 결정

## 7. Eventual consistency와 보안

### 7.1 전파 지연이 곧 노출 창

취소가 만들어진 시각부터 모든 게이트웨이가 그것을 아는 시각까지의 간격 =
**로그아웃했는데 세션이 아직 살아있는 시간**.

성능 지표가 아니라 **보안 지표**임.

### 7.2 지연의 구성 요소

```
취소 생성 (DB 기록)
  ↓  워커 폴링 주기          최대 W
워커가 집어감
  ↓  병합 + S3 PUT           P (+ 412 재시도 시 증가)
S3에 반영됨
  ↓  게이트웨이 폴링 주기    최대 G
게이트웨이 메모리 반영

최악 지연 ≈ W + P + G  (재시도 있으면 더)
```

각 항을 줄이면 지연이 줄지만 부하가 늘어남. 파라미터 선택이 곧 이 트레이드오프임.

### 7.3 무엇이 이걸 견딜 만하게 하는가

토큰 갱신 시 DB를 직접 조회하는 경로가 안전망임.
전파가 늦어도 갱신 시점에는 반드시 걸림. 캐시는 갱신과 갱신 사이만 덮으면 됨.

**이 경로가 없으면 전파 지연이 곧 무제한 노출이 됨.** 내 구현에서 이 경로를 빼면 안 되는 이유.

**어디에 쓰이나**: 폴링 주기 결정, 7단계 전파 지연 측정

## 8. 객체 스토리지의 성질

이 설계가 왜 이런 모양인지는 S3의 제약에서 나옴.

| 성질 | 결과 |
|---|---|
| 부분 수정 불가 — 객체는 통째로 씀 | read-modify-write가 강제됨 → 3장의 lost update 문제 |
| 키를 정렬 순서로 나열 가능 | 청크 키에 타임스탬프를 넣으면 별도 인덱스 없이 범위 조회 |
| 조건부 요청 지원 | 잠금 인프라 없이 OCC 가능 |
| 강한 read-after-write 일관성 | 쓴 직후 읽으면 최신이 보장됨 |
| 대용량 스트리밍에 최적화 | 시딩이 빠름 |
| 요청당 비용·지연이 있음 | 잦은 작은 갱신은 비쌈 → 배치가 필수 |

마지막 두 줄이 30분 청킹의 이유임. 큰 걸 가끔 쓰는 패턴이 S3에 맞음.

키 설계도 여기서 나옴.

```
revocations/1755100800.bin      구간 시작 unix 초를 키에 넣음
revocations/1755102600.bin
```

고정 자리수로 0을 채워야 문자열 정렬과 시간 정렬이 일치함. 안 그러면 자릿수 바뀔 때 순서가 깨짐.

**주의**: MinIO는 S3 호환이라고 하지만 모든 기능이 같지는 않음. 특히 조건부 쓰기는 비교적 최근 기능이라 지원 여부를 확인해야 함 → 3단계 스파이크.

**어디에 쓰이나**: 청크 키 설계, 스파이크 대상 결정

## 9. 측정 방법론

7단계에서 숫자를 뽑아야 하고, 그 숫자가 velog 글에 들어감. 틀린 방법으로 재면 글이 틀림.

### 9.1 평균이 아니라 백분위

평균은 꼬리를 감춤. p50과 p99를 같이 봐야 함.
전파 지연 같은 지표는 특히 그럼 — 평균 2초인데 p99가 30초면 사용자 100명 중 1명은 30초 동안 로그아웃이 안 된 것임.

### 9.2 워밍업

Go는 첫 실행에 힙 성장, 페이지 폴트가 겹침. 측정 전 몇 회 돌려서 버림.

### 9.3 측정 대상과 도구를 섞지 않기

같은 프로세스에서 부하를 만들면서 지연을 재면 서로 간섭함. 부하 생성기를 분리하거나, 최소한 CPU를 나눠 씀.

### 9.4 Go 도구

```go
testing.B                 // 벤치마크
b.ReportAllocs()          // 할당 횟수·바이트
runtime.ReadMemStats      // 힙 사용량 (전체 STW라 자주 부르면 안 됨)
runtime/metrics           // 더 세밀하고 저렴한 대안
pprof                     // 어디에 시간·메모리가 갔는지
```

메모리 비교(5.2)를 잴 때는 `runtime.GC()` 를 부른 뒤 `HeapAlloc` 을 읽어야 GC 대기 중인 쓰레기가 안 섞임.

### 9.5 전파 지연은 시계 문제

두 호스트의 시계가 다르면 "생성 시각"과 "반영 시각"의 차이가 시계 오차를 포함함.
로컬 도커 컴포즈면 전부 같은 호스트 시계를 쓰므로 문제없음. 이 사실을 측정 문서에 적어둬야 나중에 숫자를 믿을 수 있음.

**어디에 쓰이나**: 7단계 전체

## 10. 자기 점검

구현 들어가기 전에 아래를 막힘 없이 답할 수 있어야 함.

1. stateless 세션에서 로그아웃이 왜 어려운가
2. 취소를 세션 ID가 아니라 (principal, 시각)으로 표현하면 뭐가 좋아지나
3. `If-Match` PUT이 412를 주면 내 쓰기는 어떻게 된 것인가
4. lost update가 왜 조용히 일어나고, 왜 이 시스템에서는 보안 사고인가
5. 리더 선출이 있는데도 조건부 PUT이 왜 여전히 필요한가 — 반례를 하나 들 수 있나
6. `[]byte` 밀집 배열이 객체 배열보다 GC에 유리한 이유는
7. 이진 탐색이 성립하려면 워커가 지켜야 할 불변식은 무엇인가
8. 전파 지연은 어떤 항들의 합이고, 각각을 줄이면 무엇이 늘어나나
9. 12시간 윈도우가 성립하려면 어떤 경로가 반드시 있어야 하는가
10. 청크 구간을 30초에서 5초로 줄이면 무엇이 좋아지고 무엇이 나빠지나
