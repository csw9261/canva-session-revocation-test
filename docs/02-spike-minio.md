# 스파이크: MinIO 조건부 요청 동작 확인

3단계 산출물. 개념 설명은 [00-prerequisites.md](00-prerequisites.md) 2·3장 참고.

## 목적

이 프로젝트의 정확성 전체가 조건부 PUT 하나에 얹혀 있음.

```go
err := s3.Put(key, merged, ifMatch(etag))
if isPreconditionFailed(err) { continue }   // 412 가 안 오면 이 줄이 죽은 코드
```

설계와 구현을 다 한 뒤에 "412가 안 오네"를 발견하면 되돌리는 비용이 큼.
그래서 코드 쓰기 전에 세 가지가 동시에 맞는지 확인함.

1. MinIO 가 조건부 요청을 구현했는가
2. AWS SDK for Go 가 헤더를 실어 보내는가
3. strong ETag 를 주는가 (weak 이면 `If-Match` 를 못 씀)

MinIO 는 로컬 도커 단독 기동. 게이트웨이·워커 없이 스파이크 프로그램만 붙음.

## 결론

**세 가지 모두 확인됨. 설계를 조건부 PUT 기반으로 진행해도 됨.**

- SDK 의 `PutObjectInput` 에 `IfMatch` / `IfNoneMatch` 필드가 이미 있음 → 미들웨어로 헤더를 직접 넣는 우회 불필요
- MinIO 가 `PreconditionFailed` (412) 와 `304 Not Modified` 를 규격대로 반환
- ETag 가 strong (`W/` 접두사 없음)
- 조건부 PUT 이 실제로 lost update 를 막음 — 아래 B 참고

## A. 기본 동작

| # | 시나리오 | 기대 | 실제 | 결과 |
|---|---|---|---|---|
| 1 | 기본 PUT | 200 | 200 | ok |
| 2 | ETag 가 strong (`W/` 없음) | true | true | ok |
| 3 | `If-Match` 일치 PUT | 200 | 200 | ok |
| 4 | `If-Match` 불일치 PUT | 412 | 412 | ok |
| 5 | `If-None-Match: *` 신규 생성 | 200 | 200 | ok |
| 6 | `If-None-Match: *` 기존 키 | 412 | 412 | ok |
| 7 | 조건부 GET 미변경 | 304 | 304 | ok |
| 8 | 조건부 GET 변경됨 | 200 | 200 | ok |
| 9 | 변경 후 본문 수신 | `v4` | `v4` | ok |

4번과 6번의 에러 코드는 둘 다 `PreconditionFailed`.
ETag 예시: `"6654c734ccab8f440ff0825eb443dc7f"` — 단일 PUT 이라 본문 MD5 와 일치하는 형태.

**AWS SDK 는 304·412 를 에러로 반환함.** 성공 경로에서 상태 코드를 볼 수 없으므로 에러에서 꺼내야 함.

```go
var re *awshttp.ResponseError
if errors.As(err, &re) { return re.HTTPStatusCode() }
```

이걸 모르면 304 를 실패로 처리해서 폴링이 매번 에러 로그를 뱉게 됨. 구현에서 주의할 지점.

## B. 조건부 PUT 이 실제로 유실을 막는가

A 는 "API 가 규격대로 응답한다"까지만 봄. 실제로 확인하고 싶은 건 "그래서 데이터가 안 사라진다"임.

워커 여러 개가 같은 객체에 read-modify-write 를 반복하게 함.
레코드는 8바이트 uint64 하나이고, 최종 객체 크기 / 8 이 살아남은 건수임.

| workers | iters | 기대 건수 | 유실 (조건부 없음) | 유실 (조건부 사용) | 412 충돌 |
|---|---|---|---|---|---|
| 3 | 20 | 60 | 30 | **0** | 2 |
| 3 | 50 | 150 | 4 | **0** | 6 |
| 6 | 20 | 120 | 93 | **0** | 15 |
| 6 | 50 | 300 | 206 | **0** | 22 |
| 12 | 20 | 240 | 208 | **0** | 42 |
| 12 | 50 | 600 | 483 | **0** | 104 |

두 방향 모두 확인됨.

- **조건부 없으면 실제로 유실됨** — 실험 설계가 유효하다는 증거. 여기가 0이면 경쟁이 안 일어난 것이라 뒤 결과도 의미가 없음
- **조건부 쓰면 모든 조건에서 유실 0** — 안전장치가 실제로 일함

## 관측하며 눈에 띈 것

### 유실률이 워커 수를 따라감

이론적으로 워커 N개가 완전히 겹쳐 돌면 라운드마다 1개만 살아남아 유실률이 `(N-1)/N` 에 수렴함.

```
N=3   이론 67%    실측 50%, 3%
N=6   이론 83%    실측 78%, 69%
N=12  이론 92%    실측 87%, 81%
```

워커가 많아질수록 이론값에 붙음. N=3 은 변동이 큼(50% 와 3%) — 워커가 적으면 우연히 서로 안 겹치는 구간이 생기기 때문으로 보임.
**이건 해석이고, 타이밍을 직접 계측해 확인한 것은 아님.**

### 412 충돌이 예상보다 적음

워커 3개에서 조건부 없이 30건이 유실될 정도로 경쟁이 심했는데, 조건부를 켜면 충돌이 2회뿐이었음.
처음엔 충돌 카운트 버그를 의심했으나, 경쟁 수준을 올리니 2 → 15 → 42 → 104 로 정직하게 늘어나므로 계측은 맞음.

**낙관적 동시성 제어가 스스로 워커를 엇갈리게 만드는 것으로 보임.** 412 를 받은 워커는 재시도로 GET+PUT 왕복이 한 번 더 붙어 위상이 밀리고, 그 뒤로는 서로 안 겹치는 구간에서 돌게 됨.
이것도 해석이며, 요청 타임스탬프를 찍어 확인하지는 않았음.

사실이라면 실전에서 좋은 성질임 — 충돌이 자기 자신을 줄임. 다만 워커가 많아지면 (12개) 엇갈릴 여지가 줄어 충돌이 다시 늘어남.

### 확인하지 않은 것

- **304 응답의 실제 절감 바이트** — 상태 코드만 확인했고 전송량은 재지 않았음. 조건부 GET 의 목적이 대역폭 절감이므로 7단계에서 폴링 비용을 잴 때 함께 측정할 항목
- 재시도 백오프 없이 즉시 재시도했음. 워커가 많아질 때 백오프가 충돌을 얼마나 줄이는지는 미측정

## 설계에 확정할 사항

4단계로 넘기는 결론.

| 항목 | 결정 |
|---|---|
| 청크 갱신 동시성 제어 | `If-Match` 조건부 PUT + 412 재시도. 대안 검토 불필요 |
| 새 청크 생성 | `If-None-Match: *` 로 중복 생성 방지 |
| 게이트웨이 폴링 | `If-None-Match: <etag>` 조건부 GET, 304 는 정상 경로로 처리 |
| 리더 선출 | 불필요. 조건부 PUT 만으로 유실 0 확인됨 |
| 재시도 정책 | 백오프 + 지터 + 상한을 두되, 워커 3개 규모에서는 충돌이 드물어 단순하게 시작 |
| SDK 에러 처리 | 304·412 를 에러 경로에서 상태 코드로 판별하는 헬퍼를 공용으로 둘 것 |

## 재현 방법

```bash
cd spike
docker compose up -d
go build -o spike . && ./spike
```

경쟁 수준을 바꿔 관측:

```bash
SPIKE_WORKERS=12 SPIKE_ITERS=50 ./spike
```

정리:

```bash
docker compose down
```
