# Canva 세션 취소 아키텍처 정리

출처: [Session revocations at scale](https://www.canva.dev/blog/engineering/session-revocations-at-scale/) — Llew Vallis, Canva Engineering Blog, 2026-07-22

원문 주장을 검증하는 것이 목적이 아니라, 설계 의도를 이해해서 같은 방식으로 직접 구현하기 위한 노트임.
개념 설명은 [00-prerequisites.md](00-prerequisites.md), 실제 구현 설계는 [03-design.md](03-design.md)에 분리.

## 0. 한눈에

| | 이전 | 이후 |
|---|---|---|
| 취소 목록 출처 | MySQL 직접 조회 | S3 청크 다운로드 |
| 메모리 표현 | Java 객체 여러 개/건 | 16바이트 밀집 배열 |
| 조회 | 객체 컬렉션 | 정렬 배열 이진 탐색 |
| DB 부하 결정 요인 | 게이트웨이 pod 수 × 시간창 내 쓰기 수 | 쓰기 처리량과 사이트 트래픽 |
| read replica | 다수 | 2개 (이중화 목적) |
| 캐시 메모리 | 기준 | 87.5% 감소 |

## 1. 문제 배경

### 세션 모델

Canva는 세션 정보를 **암호화된 브라우저 쿠키**에 담음 — 사용자 ID, 권한, 역할까지 전부.
쿠키가 암호화돼 있으므로 게이트웨이는 매 요청마다 네트워크 데이터스토어를 조회하지 않고 그 내용을 신뢰함.

이것이 stateless 세션의 이득이자 대가임.

- 얻는 것: 요청당 조회 0회
- 잃는 것: 발급한 쿠키를 회수할 방법. 로그아웃하거나 권한이 바뀌어도 쿠키 자체는 여전히 유효함

### 취소 목록

그래서 각 게이트웨이가 "취소된 세션" 기록을 들고 있어야 함. 네트워크 조회보다 빠르고 신뢰할 수 있다는 이유로 **인메모리 조회**를 선택.

메모리에 보관하는 범위는 **12시간분**.

### 왜 12시간이면 충분한가 — 설계의 숨은 기둥

세션 쿠키가 주기적으로 갱신되고, **갱신 시점에는 MySQL을 직접 조회**함.
즉 인메모리 캐시는 "갱신과 갱신 사이 구간"만 덮으면 되고, 그보다 오래된 취소는 이미 갱신 과정에서 걸러졌음.

> Tokens that need refreshing will always be checked against the database

이 전제가 없으면 캐시가 전체 이력을 덮어야 하고, 12시간이라는 유한한 윈도우도, 오래된 청크를 버린다는 발상도 성립하지 않음.
**내 구현에서도 이 갱신 경로를 같이 만들어야 윈도우 축소가 정당해짐.**

### 규모

- 사용자 세션 수억 개
- 세션 확인 초당 수십만 회
- 게이트웨이 pod 수백 개
- 게이트웨이 1대가 부팅 시 끌어오는 취소 100만 건 이상

## 2. 무엇이 병목이었나

읽기 자체는 쌌음. 문제는 **캐시를 채우는 것(seeding)** 이었음.

배포할 때마다 게이트웨이 pod 수백 개가 동시에 부팅하면서 각자 MySQL에서 100만+ 행을 끌어감.
원문 표현으로 "coordinated stampede on our database".

부하 구조를 보면 문제가 명확함:

```
DB 부하 ∝ (게이트웨이 pod 수) × (시간창 내 취소 수)
```

두 항 모두 서비스 성장에 따라 커지고, 곱해짐. read replica를 잔뜩 붙이면 잠깐 막을 수 있지만 근본 해결이 아님.
게다가 이 부하는 사용자 트래픽과 무관하게 **배포할 때마다** 발생함.

목표는 두 가지였음.

1. 요청당 인메모리 조회의 속도·신뢰성은 유지
2. 시딩 시 DB 과부하 제거 (겸사겸사 메모리 사용량도 줄이면 좋음)

## 3. 검토 후 기각 — Redis

읽기 확장의 표준 해법은 DB와 읽는 쪽 사이에 캐시를 두는 것. 후보로 Redis 검토.

구상: 게이트웨이가 부팅 시 Redis에 전체 데이터셋을 요청하고, 이후 주기적으로 폴링해 최신 상태 유지.

기각 이유:

- Redis는 보통 **완전한 durable 구성으로 배포하지 않음**
- Redis 클러스터 자체를 운영해야 함
- 결국 문제를 한 데이터스토어에서 다른 데이터스토어로 옮기는 것에 불과하고, 캐시 일관성 유지라는 복잡도만 추가됨

여기서 요구조건이 도출됨: **강한 durability + 대용량 읽기 효율**.

## 4. 채택 — S3

S3는 크고 durable하게 저장된 파일을 싸게 서빙하도록 설계된 물건이라 요구조건에 맞음.

문제는 **취소 목록이 정적 blob이 아니라 이동하는 윈도우**라는 것. 객체 스토리지에 어떻게 올릴 것인가가 핵심 난제.

### 4.1 청킹

윈도우를 **30분 단위로 분할**하고, 각 구간을 S3 객체 하나로 대응시킴.

```
S3 버킷 — 30분마다 객체 하나씩 계속 쌓임

  revocations/1755043200.bin   09:00~09:30   ┐
  revocations/1755045000.bin   09:30~10:00   │ 12시간보다 오래됨
  revocations/1755046800.bin   10:00~10:30   ┘ 게이트웨이가 안 받음 (지울 필요도 없음)
- - - - - - - - - - - - - - - - - - - - - -   컷오프 = now − 12h
  revocations/1755048600.bin   10:30~11:00   ┐
  revocations/1755050400.bin   11:00~11:30   │
             ...                   ...        │ 게이트웨이가 받는 범위 (청크 24개)
  revocations/1755090600.bin   22:30~23:00   │
  revocations/1755092400.bin   23:00~23:30   ┘ ← 현재 청크. 워커가 계속 갱신 중
```

시간이 지나면 창이 통째로 한 칸씩 밀림.

```
  t      :  [10:00] [10:30] [11:00]  ...  [22:30] [23:00]
                    └────── 메모리에 보관 (24개) ──────┘

  t+30분 :  [10:00] [10:30] [11:00]  ...  [23:00] [23:30]
                             └────── 메모리에 보관 ──────┘
                    ↑ 폐기                          ↑ 새로 생성
```

이 선택으로 얻는 것:

- 오래된 취소를 개별 삭제할 필요 없음 — 게이트웨이가 최근 청크만 가져가면 오래된 건 자연히 무시됨
- 갱신 단위가 작아짐 — 전체 윈도우가 아니라 30분치만 다시 씀

남는 비용: 그럼에도 취소 1건을 추가하려면 수십만 건이 든 청크를 **통째로 내려받아 다시 올려야** 함. 이건 5장의 워커에서 다룸.

### 4.2 바이너리 포맷

취소 1건의 필수 정보 두 가지:

- **principal** — 누구에게 적용되는가
- **login timestamp** — 언제 이전에 시작된 세션까지 적용되는가

비트 조작으로 이 둘을 **16바이트**에 팩.

```
레코드 1건 = 16바이트

  ┌───────────────────────────┬──────────────────┬─────────┐
  │        principal          │  login timestamp │  flags  │
  └───────────────────────────┴──────────────────┴─────────┘
  ←──────────────────── 합쳐서 16바이트 ────────────────────→
```

원문은 정확한 비트 배치를 밝히지 않고 "some bit twiddling"이라고만 함.
내 구현의 배치는 [03-design.md](03-design.md)에서 확정함.

청크는 이 16바이트 원소의 **flat 배열**이고, **principal 기준으로 정렬**돼 있음.

```
청크 파일 내부

  offset:   0        16       32       48       64       80
            ├────────┼────────┼────────┼────────┼────────┤
            │ rec 0  │ rec 1  │ rec 2  │ rec 3  │ rec 4  │  ...
            └────────┴────────┴────────┴────────┴────────┘
 principal:   1002     1002     4871     9330    12045
                  └──┬──┘
                     같은 principal이 연속으로 올 수 있음 (로그아웃 여러 번)
            ──────────────────────────────────────────────→ 오름차순
```

정렬돼 있으므로 특정 principal에 대한 취소를 **이진 탐색**으로 찾을 수 있음.

```
principal 4871에 대한 취소 찾기

  index:      [0]    [1]    [2]    [3]    [4]    [5]    [6]
  principal:  1002   1002   4871   4871   9330  12045  20117
                             ↑
                     lower_bound(4871) = 2
                     여기서부터 principal이 바뀔 때까지 순회 → [2], [3]

  비교 횟수: log2(7) ≈ 3회.  100만 건이어도 20회
```

여기서 중요한 것은 게이트웨이가 하는 일이 **다운로드뿐**이라는 점임.

```
  S3에서 받은 바이트  →  []byte 그대로 보관  →  offset 계산으로 직접 접근
                          (역직렬화 단계 없음)
```

이 포맷이 주는 이득:

- 캐시 로딩 비용이 **S3 다운로드뿐** — 게이트웨이는 내려받은 바이트를 다른 표현으로 변환하지 않고 그대로 씀
- 메모리 사용량 **87.5% 감소** (8분의 1). 이전에는 취소 1건마다 Java 객체 여러 개를 썼기 때문

### 4.3 플래그 비트

실제로는 취소 타입이 여러 개임.

- 로그아웃시키지 않고 쿠키에 캐시된 정보만 무효화
- 개인이 아니라 조직 전체를 대상

(원문 용어는 brand — Canva 제품에서 팀/조직 워크스페이스를 가리킴.
이 노트와 구현에서는 범용 용어인 **조직**으로 씀)

그래서 비트 몇 개를 플래그로 예약.

```
flags 비트 (구성 예시)

  ┌────┬────┬────┬──────────────────────────┐
  │ b0 │ b1 │ b2 │          예약             │
  └────┴────┴────┴──────────────────────────┘
    │    │    └── 대상이 조직 (개인 아님)
    │    └─────── 쿠키 캐시 정보만 무효 (로그아웃은 아님)
    └──────────── 전체 로그아웃
```

**principal 기준 정렬만 유지되면** 여러 타입을 한 배열에 섞어 담아도 이진 탐색이 성립함.

```
  principal:   1002       1002       4871       9330
  flags:      로그아웃    정보무효    로그아웃     조직
              ─────────────────────────────────────→ principal 오름차순 (불변식)

  조회: principal로 구간을 찾고 → 그 구간을 순회하며 플래그별로 판정
```

정렬 기준이 principal 하나뿐이라 타입을 늘려도 자료구조를 나눌 필요가 없음.
타입별로 배열을 따로 두면 조회 때마다 배열 수만큼 탐색해야 하는데, 그걸 피한 것.

## 5. 청크를 최신으로 유지 — 워커

취소가 생길 때마다 청크를 다시 쓰는 건 지나치게 비쌈. 그래서 **비동기 워커**에 위임.

워커 루프:

```
1. DB를 스캔해 아직 S3에 안 올라간 취소를 큰 배치로 조회
2. 최신 청크를 가져옴 (시간이 충분히 지났으면 새로 생성)
3. 정렬 배열에 새 취소들을 삽입
4. 청크 재업로드
```

### 5.1 다중 워커와 데이터 경쟁

가용성과 배포를 위해 워커를 **여러 개** 동시에 돌림. 순진하게 구현하면 S3에 대한 데이터 경쟁이 생기고, 대표적으로 **lost update** — 취소가 조용히 사라짐.

취소 시스템에서 이건 성능 문제가 아니라 보안 사고임. 로그아웃했는데 세션이 계속 살아있고, 로그에도 흔적이 안 남음.

### 5.2 조건부 PUT으로 OCC

**조건부 PUT 요청**으로 낙관적 동시성 제어(optimistic concurrency control) 구현.

- 모든 청크 갱신에 "처음 읽은 이후 이 청크가 바뀌지 않았다"는 전제 조건을 붙임
- 새 청크 생성에도 유사한 검사를 붙여 다른 프로세스가 이미 같은 청크를 만들지 않았음을 보장

보장되는 것: 각 read-modify-write가 **S3의 취소 집합에 추가만** 하게 되고, 실행이 인터리빙돼도 데이터가 유실되지 않음.

(조건부 요청이 무엇이고 왜 이게 성립하는지는 [00-prerequisites.md](00-prerequisites.md) 참고)

### 5.3 리더 선출은 정확성이 아니라 최적화

ZooKeeper 리더 선출도 쓰지만, **충돌이 계속 나서 시스템에 부하를 주는 것을 막는 최적화**일 뿐임. 정확성을 여기에 의존할 수 없음.

원문이 든 반례가 정확함: 어떤 노드가 **쓰기 직전에 임의의 시간 동안 멈출** 수 있음. 그 사이 다른 노드가 새 리더가 되어 자기 변경을 씀. 원래 노드가 깨어나 쓰면 그것을 덮어씀 — PUT 조건이 없다면.

**리더 선출은 충돌 빈도를 낮추고, 정확성은 조건부 PUT이 담당함.** 이 분리가 이 설계에서 가장 배울 만한 지점.

### 5.4 O(N²)인데 왜 괜찮은가

N건짜리 청크를 만들려면 O(N²) 시간이 듦 — 고정 크기 배치를 추가할 때마다 청크 전체를 처리하므로. 게다가 lost update 문제 때문에 수평 확장도 쉽지 않음.

그런데 실제로는 **배치당 수백 건씩 처리**하면 최적화 안 한 구현으로도 **초당 2000건 이상** 쓰기 처리량이 나옴. 필요한 것보다 충분히 많음.

원문의 결론:

> Constant factors matter enormously

병목은 CPU가 아니라 **네트워크 지연**. 수십만 건짜리 배열을 다뤄도 밀집 배열 처리는 현대 하드웨어에서 너무 빨라서, S3 왕복이 시간을 다 먹음.

## 6. 청크 다운로드 — 게이트웨이

### 6.1 부팅 시딩

각 청크는 특정 30분 구간에 생성된 취소를 담음. 최근 12시간분만 필요하므로 최신 청크 일부만 받으면 됨.

**청크 키에 30분 구간의 시작 타임스탬프를 인코딩**해둠. 그래서 키를 정렬 순서로 나열하고 컷오프 타임스탬프 이후만 골라내면 필요한 청크 목록이 나옴. 별도 인덱스가 필요 없음.

### 6.2 지속 갱신

부팅 때만 받으면 이후 생기는 취소를 배포 전까지 모름. 그래서 **조건부 GET**으로 최신 청크를 폴링하되, **실제로 바뀐 경우에만** 다시 내려받음.

규모감:

> Even if we had 1 million revocations in a 30-minute window, this would only be 16 megabytes a few times per minute

게이트웨이가 프록시하는 요청·응답 데이터양에 비하면 무시할 수준.

### 6.3 만료

청크 구간의 끝이 12시간보다 오래되면 캐시에서 그냥 버림.

### 6.4 데이터양

게이트웨이 1대당 수십 MB. fleet 전체로는 수십 GB.
같은 건수를 여전히 끌어오지만, MySQL에 행을 서빙시키는 대신 S3에서 밀집 바이너리를 스트리밍하는 것이라 훨씬 빠르고 확장성 있음.

---

## 7. 결과

- 배포 속도 개선
- 취소 DB의 read replica를 **2개**로 축소 (이중화 목적만 남김)
- 인메모리 캐시 **87.5% 감소** — Java 힙에 건당 객체 여러 개를 두는 오버헤드가 사라짐
- 부하 성격이 바뀜

```
이전:  DB 부하 ∝ (게이트웨이 수) × (시간창 내 쓰기 수)     ← 배포 때 폭발
이후:  부하    ∝ (쓰기 처리량) + (사이트 트래픽)           ← 예측 가능
```

## 8. 설계 결정과 트레이드오프

| 결정 | 얻은 것 | 포기한 것 |
|---|---|---|
| 암호화 쿠키 (stateless 세션) | 요청당 DB 조회 0회 | 즉시 취소 능력 — 취소 인프라 전체가 이 대가임 |
| 인메모리 취소 캐시 | 조회가 빠르고 네트워크 장애에 강함 | 시딩 문제, 메모리 사용량 |
| 12시간 윈도우 | 캐시 크기 유한, 오래된 청크 폐기 가능 | 토큰 갱신 시 DB 조회 경로를 반드시 유지해야 함 |
| Redis 대신 S3 | durability, 대용량 읽기 효율, 운영 부담 없음 | 이동하는 윈도우를 객체로 표현하는 복잡도 |
| 30분 청킹 | 갱신 단위 축소, 만료가 공짜 | 1건 추가에도 청크 전체 재작성 |
| 16바이트 밀집 배열 | 메모리 1/8, 변환 없이 바로 사용, 이진 탐색 | 스키마 유연성 없음 — 필드 추가하려면 포맷 버전 관리 필요 |
| 비동기 워커 | 취소 생성 경로가 S3 왕복에 안 묶임 | 전파 지연 발생 (eventual consistency) |
| 조건부 PUT (OCC) | 잠금 인프라 없이 유실 방지 | 충돌 시 재시도 비용, 수평 확장 어려움 |
| 리더 선출 (최적화) | 충돌 빈도 감소 | 정확성은 여기 못 기댐 — 조건부 PUT이 여전히 필요 |

## 9. 원문을 읽으며 짚은 것

**(1) 12시간 윈도우의 전제**
토큰 갱신 시 DB를 조회한다는 경로가 이 설계 전체를 떠받침. 원문은 한 문장으로 지나가지만, 이게 없으면 유한 윈도우도 청크 만료도 성립하지 않음.

**(2) 전파 지연 수치가 없음**
취소가 생성돼서 모든 게이트웨이에 반영되기까지 실제로 몇 초인지 원문에 없음. 이건 곧 "로그아웃했는데 세션이 아직 살아있는 시간"이라 이 시스템의 가장 중요한 특성값인데도 그럼.
**내 구현에서 직접 재볼 지점.**

**(3) O(N²) 주장의 조건**
"O(N²)라도 괜찮다"는 배치를 크게 잡았을 때의 이야기임. 배치 크기가 작으면 청크 재처리 횟수가 늘어 같은 논리가 안 통함. 알고리즘 복잡도를 배치 크기라는 상수로 눌러버린 사례로 읽는 게 맞음.

**(4) 숫자 하나가 앞뒤로 어긋나 보임**
6.4절의 "over a billion rows"는 앞에서 말한 게이트웨이당 100만 건과 바로 안 맞음. 게이트웨이당 100만 × pod 수백 개 = fleet 전체 합계로 읽어야 앞뒤가 맞음. 인용할 때 주의.

## 10. 내 구현에 반영할 것

**그대로 가져갈 것**

- 16바이트 밀집 레코드, principal 정렬 flat 배열, 이진 탐색
- 시간 구간 단위 청킹, 청크 키에 구간 시작 타임스탬프 인코딩
- 비동기 워커 + 조건부 PUT 기반 OCC + 412 재시도 루프
- 게이트웨이 부팅 시딩 + 조건부 GET 폴링 + 윈도우 만료 시 청크 폐기
- 토큰 갱신 시 DB 직접 조회 경로 (윈도우 축소의 정당성)

**뺄 것**

- ZooKeeper 리더 선출 — 원문도 정확성이 아닌 최적화라고 명시. 조건부 PUT만으로 정확성 확보됨
- 조직 단위 취소, 다중 취소 타입 — 플래그 비트 자리만 남기고 타입은 1종

**축소할 것**

| 파라미터 | 원문 | 내 구현 | 이유 |
|---|---|---|---|
| 캐시 윈도우 | 12시간 | 12분 | 만료 동작을 실습 중에 관측 가능해야 함 |
| 청크 구간 | 30분 | 30초 | 위와 같은 비율 유지 (윈도우/구간 = 24) |

축소 비율을 여기 기록해두는 이유: 나중에 측정한 숫자를 원문 숫자와 나란히 놓을 때 착각하지 않기 위함.
